Downloading one file, two ways

The same 8 MB file, fetched twice from this server: once over a single connection, then again split into byte ranges fetched in parallel. Same bytes, same SHA‑256 — very different clock.

What you just watched

Nothing here is faster at computing. Both rounds move the identical 8 MB. The single connection spends nearly all of its life blocked, waiting on the network while doing no work at all. The concurrent round simply arranges for several connections to do that waiting at the same time.

The Java version of this is the real project: one CompletableFuture.supplyAsync per chunk on a dedicated executor, joined with allOf(...).thenApply(...), each chunk writing straight into its own offset of one pre-allocated file. The ranges never overlap, so there is no lock anywhere — and that is why the two SHA‑256 hashes above match.
