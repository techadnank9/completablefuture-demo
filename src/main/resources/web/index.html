One file. Two ways. Same moment.

Pick a file, then watch both sides fetch it at the same instant. The left uses a single connection; the right splits it into byte ranges fetched in parallel. Each ends up with its own copy, which you can open, play or save. They should be identical; that is the point. PNG and MP4 are both compressed, so a range written to the wrong offset would not decode at all. Getting a picture that shows, or a video that plays, means every byte arrived where it belonged.

What just happened

Neither side computed anything faster. Both moved the identical bytes. The left connection spent nearly its whole life blocked: parked on a socket, using no CPU, waiting. The right side simply arranged for several connections to do that waiting at the same time.

In the Java project this is one CompletableFuture.supplyAsync per byte range on a dedicated executor, joined with allOf(...).thenApply(...), each range writing straight into its own offset of one pre-allocated file. The ranges never overlap, so nothing needs a lock, which is why both files above carry the same hash. This page does the same with fetch and Promise.all.  Source on GitHub
